## 실패와 재실행

기존 `NotionClient`, `RunStore`, `preflight`, `relationPayload`를 재사용한 고정 실험 스크립트 `scripts/notion-poc/copy-experiment.mjs`를 준비했다. V1/기존 PoC 엔진은 바꾸지 않는다.

- 기본 `dry-run`은 네트워크 요청 0.
- 실행 ID는 `nb-v2-007b`로 고정한다. 기존 002A 상태 파일과 분리한다.
- 새 부모 ID는 `NOTION_COPY_PARENT_PAGE_ID`로 별도 지정하고 apply의 `--confirm-parent`와 일치해야 한다. 기존 002A 부모 ID로는 실행하지 못한다.
- 쓰기 전 단계를 기록하고 생성한 ID를 보존한다. 실패·응답 유실·미완료 상태는 자동 재생성하지 않는다.
- 생성 실패 시 부분 생성물을 삭제하거나 새 run-id로 우회하지 않는다. 실패 지점과 상태를 보고한다.
- 완료 실행은 추가 API 요청 없이 재사용한다. `verify-source`는 읽기 전용이며 기존 manifest를 갱신하지 않는다.

## 복제와 독립성 검증 예정

1. B가 회사가 아닌 별도 테스트 공간인지 확인한다.
2. 사용자가 세 DB가 들어 있는 묶음 페이지 전체를 복제한다. DB 하나만 따로 복제하지 않는다.
3. 복제본의 페이지/DB/데이터 소스/행 ID를 원본과 구분해 기록한다. 연결 메뉴가 원본이 아닌 복제본을 가리키는지 확인한다.
4. API 접근이 없으면 UI 확인 범위를 기록하며 API 검증 완료라고 표현하지 않는다. A의 internal token이 B를 읽을 수 있다고 가정하지 않는다.
5. 모든 참조가 복제본 내부임을 먼저 확인한다. 그 전에는 변경 실험을 하지 않는다.
6. 별도 범위 확인 후 복제본 AP02만 대기→선정으로 바꾸고 원본의 값이 그대로인지 확인한다. 이어 원본 AP03만 선정→미선정으로 바꾸고 복제본 값이 그대로인지 확인한다. 각 변경 후 재계산을 확인하고 테스트 값을 원복하는 것을 기본으로 제안한다. 이 변경 실험은 아직 실행/승인하지 않았다.
7. 실제 클릭·선택 횟수, 로그인·연결 권한 추가, 수동 수리 횟수를 기록한다. 공식 절차 단계 수를 실제 클릭 수로 대신하지 않는다.

공식적으로 같은 계정의 다른 공간은 페이지의 `옮기기` 메뉴에서 대상 공간과 위치를 선택해 복제하는 절차다. 다른 계정은 비공개 공유 후 바깥 컨테이너 내부 페이지를 선택하는 별도 절차이며 이번 기본 경로는 아니다. 링크/관계/권한 손상 가능성이 있으므로 전체 묶음 보존은 실제 실험으로 확인해야 한다. [Notion 공식 안내](https://www.notion.com/ko/help/transfer-content-to-another-account)

관련 DB 하나를 개별 복제할 때 양방향 관계가 단방향으로 바뀔 수 있다는 공식 예가 있다. 이것을 전체 묶음 복제의 성공 보장으로 해석하지 않는다. [공식 관계형 FAQ](https://www.notion.com/help/relations-and-rollups)
