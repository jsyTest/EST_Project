## 3. 실제 UI 변경

홈 `index.html`과 기존 `mapping.html`에서 ‘새 Notion DB 구성하기 → 입력 → 분석 요약 → DB 구성 미리보기’를 제공한다. 폼과 CSV를 모두 입력하도록 강제하지 않는다. CSV는 파일/텍스트 중 현재 선택한 입력만 분석한다.

설계 이름은 계정 저장·기존 V1 결과 제목에 사용하며, 새 DB 구성 미리보기에는 필수가 아니다. 일반 교육/해커톤은 저장할 수 있는 분류이며, 이번에는 두 유형별 생성 엔진·다른 스키마를 구현하지 않았다.

기존 V1의 목적·관리 모듈·추가 요구사항·결과 화면은 ‘기존 V1 설계안 미리보기’ 안에 유지했다. 이전 결과 화면에서 ‘요구사항 수정’으로 돌아와도 통합 홈에서 기존 값을 복원한다.

입력보다 위에 있던 저장 패널은 입력·결과 영역 아래로 옮겼다. 주 저장 버튼은 유지하고 목록·복사본·새 설계는 접힌 보조 영역에 배치했다.

## 4. 세 가지 입력 방식

| 입력 | 구현 및 실제 Chrome 결과 |

| 폼 단독 | 번호형 질문 파서 재사용. 폼만으로 분석·미리보기 통과 |

한쪽 입력 분석 실패를 다른 쪽 성공으로 숨기지 않는다. 번호 없는 폼을 인식하지 못하면 실패를 안내한다. 폼 질문·CSV 컬럼 모두 0개인 분석은 실패한다. 기존 직접 추가 속성의 확인 후 미리보기 경로는 유지한다.

## 5. CSV 헤더와 개인정보 보호

파일과 텍스트는 동일한 `readCsvHeader`/`firstRecord` 경로를 사용한다. BOM·한글·인용 쉼표·escaped quote·인용된 줄바꿈·헤더만 있는 입력을 처리한다. 파일은 UTF-8/EUC-KR 선택을 유지하고 첫 레코드 최대 64 KiB 제한을 유지한다. 텍스트는 이미 디코딩된 문자열이다.

응답 행의 값으로 유형이나 선택지를 추정하지 않는다. 응답 행·원본 파일·CSV 원문 텍스트를 sessionStorage나 Supabase 저장 모델에 추가하지 않는다. 분석 성공 후 텍스트 칸도 인용 처리한 헤더만 남긴다. 파일은 업로드하지 않는다.

CSV를 변경한 후 분석하지 않은 채 저장하면 이전 헤더가 새 값인 것처럼 저장되는 것을 막고 분석 후 저장하도록 안내한다. 분석 전 CSV 원문은 복원 대상이 아니다. 페이지를 떠나기 전 먼저 분석해야 헤더가 보존된다.

100자를 넘는 CSV 헤더는 원본 컬럼명을 유지하면서 추천 Notion 속성명만 100자로 줄이고 안내한다. 줄인 이름끼리 충돌하면 필수 확인으로 처리한다. 이 수정은 실제 브라우저 검사 중 발견한 저장 제한 문제를 해결한 것이다.

## 6. 분석 요약·확인 사항

폼 질문, CSV 컬럼, 최종 추천 속성, 자동 처리/확인 완료, 필수 확인 속성, 제외, 중복/충돌 표시 수를 분리했다. 최종 추천 속성 수에는 포함된 기본 운영 속성과 DB별 자동 제목 속성이 포함되며, 실제 compileSchema 결과의 속성 수와 일치하도록 검사했다. 기본 운영 속성만으로 분석 성공 처리하지 않는다.

일반 CSV 헤더는 Text를 권장하며 선택지를 만들지 않는다. 이메일·연락처 등 명확한 별칭은 Email·Phone number를 유지한다. Text 권장이나 서로 일치하지 않는 폼/CSV는 안내하고 안전한 미리보기를 허용한다. 중복 컬럼·모호한 연결·같은 DB 속성명 충돌·중복 제목·잘못된 옵션은 구조 검사로 차단한다. ‘확인 완료’를 눌러도 실제 충돌은 통과하지 않으며 요약의 필수 확인 수에도 남는다.

입력 변경 후에는 기존 스키마 내려받기를 무효화한다. 파일 읽기 중 입력이 바뀌면 오래된 분석 결과로 화면을 덮어쓰지 않는다. 저장된 폼 원문과 매핑의 질문 원문이 다르면 새로고침 후에도 재분석을 요구한다.

## 7. 고급 설정

기본은 접힘이다. 필요할 때 속성명·유형·대상 DB·포함/제외·CSV 연결·옵션·색상·Status 그룹·직접 추가·확인 상태를 편집한다. 구조 오류가 있는 상태로 미리보기를 요청하면 고급 설정을 펼친다. 명시적 장문/서술형 Text, 단일 Select, 복수 Multi-select 우선순위와 허용 색상/Status 그룹 제약은 기존 규칙을 유지했다.

기존 저장 모델의 편집값은 불러오는 즉시 재분석하거나 자동 확정하지 않는다. 기존 확인 필요 상태와 옵션 색상도 보존한다. 사용자가 ‘입력 분석하기’를 다시 누르면 기존과 같이 매핑을 새 추천값으로 바꾼다는 안내를 유지한다.

## 9. 저장·복원 호환성

원격 `education_drafts`의 제약·RLS 메타데이터를 SELECT로 확인했다. `schema_version=1`, configuration.version=1, requirements/mapping 객체, 524288바이트 제한, 제목 1~80자 조건이 존재한다. RLS enabled/forced 모두 true이며 SELECT/INSERT/UPDATE의 auth.uid() 소유권 정책이 유지되고 UPDATE는 USING·WITH CHECK 모두 존재한다. 업무 행·세션·비밀번호는 조회하지 않았다.

version 1은 유지한다. `requirements.educationType`만 선택적으로 허용하고 과거 값이 없으면 `education`으로 읽는다. 기존 매핑/컬럼/옵션/색상 형식은 유지하며 새 테이블·SQL·RLS 변경이 필요하지 않다.

자동 검사와 실제 Chrome의 가상 서버에서 이름·유형·목적·모듈·헤더·매핑·사용자 속성명·옵션 색상을 저장/복원했다. Chrome에서는 임시 캐시 제거 후 가상 저장 행을 URL로 열어 복원하는 흐름도 통과했다. **실제 Supabase에 이번 UI로 INSERT/UPDATE하거나 실제 두 계정 RLS를 재검증한 결과는 아니다.**
