# [NB-V2-UI-009 작업 보고서] Production 실계정 QA

## 결론

**부분 확인 완료, 전체 통과 판정 보류.** 이번에는 사용자 Chrome의 기존 본인 관리자 세션에 실제로 접근하여 관리자 메뉴·서비스 복귀·본인 설계 열기·새로고침·로그아웃·로그아웃 후 관리자 URL 차단을 조작했다. 자동 검사를 다시 돌린 결과로 대체하지 않았다.

다만 사용자의 새 로그인 입력 과정, 실제 일반 계정의 API 403, 모바일 로그인 헤더는 미검증이다. 또한 작업 중 외부 Git/배포 변경이 발생했다. 처음 요청한 배포와 종료 시점 운영 배포를 같은 것으로 처리하지 않는다.

## 2. 실계정 확인 완료

연결 방법: cua_repl의 macOS Chrome 앱 UI. 브라우저 확장 연결 대신 네이티브 앱의 접근성 화면과 실제 스크린샷을 사용했다. 별도 프로필 파일/쿠키/세션 저장소/개발자 도구/네트워크 인증 헤더는 열지 않았다. 기존 본인 관리자 계정의 이메일이 화면에 표시되는 것을 확인했다. 보고서에는 이메일 원문을 반복 저장하지 않는다.

관리자 확인 완료 UI는 실제 서버 권한 확인을 사용하는 앱의 결과다. 이번에 인증 헤더/네트워크 패널을 열지 않았으므로 관리자 API의 HTTP 200 원문을 직접 캡처했다고 보고하지 않는다.

## 3. 기존 자동 검사에서만 확인

- NB-V2-UI-008에서 실행한 Node 326/326, 그 안의 V1 256조합은 **이전 작업 기록**이다. UI-009에서는 전체 자동 검사를 다시 실행하지 않았다.
- 일반 계정의 서버 관리자 403, 클라이언트 user_metadata 위조 거절, 지연 응답·역할 회수·계정 전환 모의 검사는 그 기존 테스트 증거에 한정한다.
- 이전 Chrome 정적 모형/로컬 시연의 모바일 4해상도 검증도 운영 실계정 모바일 확인을 대신하지 않는다.
- 이전 UI-008의 무인증/무효 Bearer API 거절 결과를 이번 새 실계정 API 검사라고 표시하지 않는다.

## 4. 미검증

1. 사용자가 로그인 폼에서 직접 새로 로그인하는 단계: 기존 세션을 사용했고, 로그아웃 후 재로그인 확인 요청에 아직 답변 없음. 비밀번호를 대신 입력하거나 읽지 않았다.
2. 실제 일반 사용자 테스트 계정의 로그인, 버튼 숨김, 관리자 직접 URL 차단, 관리자 API 403. 기존 일반 계정의 사용 가능 여부를 질문했으며 새 계정을 만들지 않음.
3. 실제 모바일 로그인 상태의 헤더·복귀 버튼·KPI 배치. 데스크톱 창의 시각 확인만 완료. 모바일 확인 요청에 아직 답변 없음.
4. 고정된 최신 배포 dpl_Fa37Zvqdv75kCkJYCC9KFkR5C1PG에서 처음부터 끝까지 재실행한 QA. 배포가 중간 변경되어 전환 전후를 단일 결과로 합치지 않음.
5. 실제 API 요청 상태 코드 원문, 두 실사용자 간 설계 격리, 모든 매핑/색상 필드의 원본 비교는 이번 범위에서 미실행.

사용자에게 묻는 것은 결과·사용 가능 여부뿐이며 JWT/쿠키/비밀번호 붙여넣기를 요구하지 않았다. 직접 재로그인을 요청한 뒤에는 입력 중인 비밀번호를 관찰하지 않도록 추가 브라우저 조회를 하지 않았다.

## 5. 오류 발견 — 구화면 표시/갱신 불일치

실제 기존 Chrome 관리자 창에서 이전 복귀 링크와 자기 링크가 남아 있는 현상을 관찰했다. 최신 공개 HTTP 파일과 달랐으며 단순 새로고침에서는 접근성 트리에 변화가 없었다. 강력 새로고침 후 최신 단일 복귀 UI로 바뀌었다.

- 재현한 흐름: 기존 로그인 관리자 창 관찰 → 로고 옆 복귀/관리자 자기 링크/사이드바 복귀 표시 → 새로고침 클릭 후 동일 트리 → Cmd+Shift+R → 단일 오른쪽 복귀·자기 링크 없음 → 권한 확인 완료.
- 기대: 현재 배포의 단일 복귀 UI 표시.
- 실제: 기존 창에서는 구 UI가 보였고 강력 새로고침 후 해소.
- 원인: 브라우저 캐시/기존 문서 잔존 가능성이 있으나 정확한 원인 미확정. CDN 오류·서버 코드 오류로 단정하지 않는다.
- 독립 읽기 확인: admin.html·js/auth.js·css/auth.css·index.html HTTP 200 및 당시 로컬 소스 바이트 일치. 최신 admin.html은 복귀 문구 1개·옛 사이드바 복귀 없음.
- 상태: 현상 관찰 완료, 강력 새로고침 후 현재 창에서 해소, 새 배포/다른 브라우저의 재현성 미검증.
- 조치: 코드·캐시 정책·배포 설정 변경 없음. 재발하면 해당 창/접속 시각/일반 및 강력 새로고침 결과부터 수집하는 후속 진단을 제안.

초기 다른 Chrome 창에서 주소 타이핑이 잘못 반영된 네트워크 오류도 있었으나 실제 대상 도메인 오류와 구분했다. 브라우저 보안 경고 우회는 하지 않았다.

## 6. 사용자에게 남은 짧은 확인

1. 현재 운영 로그인 화면에서 본인이 직접 로그인 후 교육 설계 화면이 보이는지만 알려준다. 비밀번호/토큰 불필요.
2. 휴대폰 로그인 화면과 로그인 후 헤더에서 버튼·이메일이 겹치거나 잘리는지 알려준다.
3. 기존 일반 계정을 쓸 수 있다면 사용자가 직접 계정 전환한다. 화면 비노출만으로 API 403까지 성공 처리하지 않는다. 자격 증명을 읽지 않는 안전한 요청/상태 확인 방법이 확보되어야 API 거절 판정을 한다.

재로그인 답변이 없으면 미검증을 유지한다. 현재 사용자 브라우저의 마지막 관찰 상태는 로그아웃된 로그인 화면이다. 이후 사용자가 직접 변경한 상태는 관찰하지 않았다.

## 7. 보존 및 결과물

앱/테스트/JPEG 수정 0, Git commit/push/checkout/reset/clean 0, Vercel 배포/alias/환경변수 변경 0, Supabase 설정/RLS/역할·업무 데이터 변경 0, Notion 요청/쓰기 0. 사용자가 요청한 기존 앱 로그아웃은 실제로 실행했다. 이는 Auth 정책/관리자 역할 변경이 아니다.

시작에 있던 UI-008 문서 2개를 덮어쓰지 않았다. 외부에서 e6512eb로 커밋된 이후에는 그 상태를 보존했다. 이번 새 로컬 파일은 이 보고서와 UI-009 인계문뿐이다. 기존 미커밋 변경을 정리하거나 강제 복원하지 않았다.

데스크톱 앱 스크린샷을 도구에서 직접 검토했지만 이번에 새 로컬 PNG 파일을 저장하지 않았다. 정확한 CSS 뷰포트 크기나 모바일 해상도 캡처를 확보했다고 주장하지 않는다.
