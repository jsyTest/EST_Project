# NB-V2-007B 사용자 수동 테스트 안내

현재는 별도 테스트 워크스페이스 B가 없어 **실행하지 않는 안내문**이다. 회사 공간을 선택하지 않는다. B가 준비됐다는 사용자의 확인 뒤에만 조건부 승인 범위를 적용한다. 새 워크스페이스 생성이나 회사 연결은 이번 작업에 포함되지 않는다.

## 1. 시작 조건

다음 세 가지를 먼저 확인한다.

1. 원본 A와 다른 **개인 테스트 공간 B**의 이름 및 같은 계정인지 여부.
2. B에서 페이지를 만들 수 있는 권한. 복제본을 API로 검사하려면 B 전용 연결도 별도로 필요할 수 있다. 원본 토큰이 B를 읽는다고 가정하지 않는다.
3. 원본 생성 계획 `NB-V2-007B_TEST_PLAN.md` 범위가 그대로인지 확인. 바뀌었으면 변경 범위를 검토한다.

## 2. 별도 원본 준비

조건 충족 후 개인 A에 비공개 `[TEST] NB-V2-007B 실험실`을 만들고, 그 안의 복제용 묶음 페이지에 DB 3개와 가상 행 7개를 만든다. 기존 002A 영역은 부모로도 사용하지 않는다. 필요한 경우 사용자가 새 실험실 페이지에 기존 생성 연결을 직접 추가한다. 토큰을 채팅에 붙여넣지 않는다.

기본 명령은 실행해도 원격에 쓰지 않는다.

```sh
node scripts/notion-poc/copy-experiment.mjs dry-run
```

별도 실험실 UUID가 정해지고 접근을 확인한 후 사용할 명령 형태다. **아래는 현재 실행 지시가 아니며 승인 조건 충족 후의 예시다.** `NOTION_COPY_PARENT_PAGE_ID`는 기존 002A 환경변수와 분리한다.

```sh
NOTION_COPY_PARENT_PAGE_ID=<새-개인-실험실-UUID> node --env-file=.env scripts/notion-poc/copy-experiment.mjs preflight
NOTION_COPY_PARENT_PAGE_ID=<새-개인-실험실-UUID> node --env-file=.env scripts/notion-poc/copy-experiment.mjs apply --confirm-parent <새-개인-실험실-UUID>
NOTION_COPY_PARENT_PAGE_ID=<새-개인-실험실-UUID> node --env-file=.env scripts/notion-poc/copy-experiment.mjs verify-source
```

원본 검증이 통과하지 않으면 복제로 진행하지 않는다. 실패한 실행 ID를 바꾸거나 상태 파일을 지워 재생성하지 않는다.

## 3. 같은 계정의 다른 공간 B로 복제

1. 원본의 **사람·프로그램·신청기록 DB 3개가 모두 들어 있는 묶음 페이지**를 연다.
2. 원본의 페이지/DB 링크와 기준값을 기록한다.
3. 묶음 페이지의 `•••` → `옮기기`를 선택한다.
4. 워크스페이스 선택에서 개인 테스트 B를 선택한다. 회사 이름이면 중단한다.
5. B 내부의 저장 위치를 선택하고 복제 확인을 진행한다.
6. 생성된 복제본 링크와 실제 버튼/선택 횟수를 기록한다. 이름이 같아도 원본 링크와 새 링크가 다른지 확인한다.

Notion 공식 절차는 공간 간 이동 시 복제본을 만들고 원본을 남기는 방식이며, 링크·관계·권한 등의 손상 가능성을 안내한다. 메뉴 표현과 클릭 수는 실제 UI에서 확인해야 한다. [공식 안내](https://www.notion.com/ko/help/transfer-content-to-another-account)

공식 문서는 DB 하나만 개별 복제할 때 양방향 관계가 단방향으로 바뀌는 예를 설명한다. **이번 기본 실험에서는 DB 하나씩 복제하지 않는다.** 개별 DB 비교 실험은 추가 복제 생성 범위를 먼저 정한 후 별도로 진행한다. [관계형 FAQ](https://www.notion.com/help/relations-and-rollups)

## 4. 복제본 체크리스트

| 항목 | 확인 방법 | 통과 기준 |
| --- | --- | --- |
| 구조 | 실제 DB를 하나씩 열기 | DB 3개, 사람 2행·프로그램 2행·신청 3행 |
| 속성 | 속성 설정 열기 | 이름·유형, Select 옵션·색상, Status 3그룹 일치 |
| 사람 관계 | AP01/AP02의 사람 연결 및 P01의 역관계 | P01↔AP01/AP02, P02↔AP03 |
| 프로그램 관계 | 신청과 프로그램 양쪽에서 열기 | C01↔AP01/AP03, C02↔AP02 |
| 대상 독립성 | 관계 속성 편집 및 연결 메뉴에서 대상 DB 열기 | 대상 링크가 B의 복제본 DB. A의 원본 링크가 남지 않음 |
| 양방향 | 관계 설정과 양쪽 행 확인 | 역방향 속성이 있고 실제 행이 서로 연결됨 |
| Rollup | 속성의 관계·대상·집계 방식과 숫자 보기 | P01/P02 신청 2/1, C01/C02 신청 2/1, 선정 2/0 |
| Formula | 식과 결과 확인 | C01/C02 선정률 100/0, 신청별 선정 값 1/0/1 |
| 외부 참조 | 관계·수식·보기 대상 링크 확인 | 묶음 밖 원본 DB/페이지 참조 없음 |

같은 화면에 숫자가 보이는 것만으로 내부 ID 일치를 입증했다고 하지 않는다. UI만 확인했다면 UI 결과로 적고, API에서 관계의 data_source_id·역방향 property ID·Rollup 대상 ID를 확인하지 못했다면 해당 항목은 API 미검증으로 남긴다.

## 5. 독립성 변경 실험 — 별도 범위 확인 후

이번 원본 생성 조건부 승인에는 이 변경 실험이 포함되지 않는다. 복제본 링크·대상·가상 행을 확인하고 변경/원복 범위를 승인받은 뒤 진행한다.

1. 복제본 내부 참조가 먼저 확인돼야 한다. 원본을 가리키면 변경하지 않는다.
2. B의 AP02만 대기→선정으로 바꾼다. B의 P01 선정 건수 2, C02 선정 건수 1/선정률 100, 선정 고유 사람 2인지 본다. A는 기준값 그대로여야 한다.
3. A의 AP03만 선정→미선정으로 바꾼다. A의 P02 선정 건수 0, C01 선정 건수 1/선정률 50, 선정 고유 사람 1인지 본다. B는 직전 값 그대로여야 한다.
4. 승인 범위대로 두 값을 원복하고 양쪽 기준값이 돌아왔는지 확인한다.
5. 전파가 늦으면 잠시 후 읽기 재확인한다. 응답을 못 받았다고 같은 변경을 자동 반복하지 않는다.

## 6. 다른 계정 경로

기본은 비공개 방식이다. 공유 대상 계정·권한·노출되는 가상 자료 범위를 설명한 후 별도 승인을 받는다. 공식 절차는 바깥 공유 페이지에 Full access로 초대한 뒤 받은 계정에서 **안쪽 페이지**를 선택해 이동·복제한다. 공개 템플릿 전환은 기본값이 아니다. [공식 계정 간 안내](https://www.notion.com/ko/help/transfer-content-to-another-account)

이번에는 초대·공개·권한 변경이나 다른 계정 로그인을 하지 않았다.

## 7. 기록 양식과 판정

```text
대상 B / 계정 경로:
원본 묶음 URL / 복제본 URL:
실제 클릭 횟수 / 선택 횟수 / 로그인 횟수:
추가 연결·공유 권한 작업:
DB·속성·색상·Status:
관계 대상 ID / 양방향:
Rollup·Formula 식 / 실제 값:
원본 참조 잔존:
B 변경→A 유지:
A 변경→B 유지:
원복 확인:
수동 수리한 항목·횟수:
완료 / 부분 완료 / 미검증 / 실패:
```

현재 실제 클릭 수는 미측정이다. 매번 관계·수식을 수동 수리해야 한다면 간편 생성의 성공으로 판정하지 않는다. 전체 묶음이 수리 없이 통과하면 A 방식 채택 후보, 단일 DB만 통과하면 B 방식, 관계형 전달이 실패하거나 수동 수리가 과하면 C(OAuth 직접 생성) 우선 검토로 연결한다. 현재는 어떤 복제 경로도 실제 통과 판정을 내리지 않는다.
