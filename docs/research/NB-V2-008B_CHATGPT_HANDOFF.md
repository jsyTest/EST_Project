## 구현

기존 v1 매핑을 정규화한 뒤 독립 planVersion:1 생성 계획을 만듭니다. DB/DS/속성/정·역 관계/계산/옵션을 안정적인 논리 ID로 참조합니다. 같은 입력·설정은 같은 planId와 JSON을 만들며 DB 표시명을 바꿔도 내부 참조는 유지됩니다.

- 기본형: 기본값, 신청·참가 DB 1개. 관계/KPI 없음. 입력 없는 연락처/날짜를 임의 추가하지 않음.
- 일반형: 사람·프로그램·신청 3DB, 두 양방향 관계, 신청 건수 Rollup/Formula 계획.
- 확장형: 참여·출석·팀·제출물·심사·수료·설문의 의존성을 따라 필요한 DB만 추가.
- 교육/해커톤은 공통 모델과 알려진 운영 유형 옵션을 사용.
- 헤더만 보고 3DB나 사람 식별을 확정하지 않음. 운영 조건을 명시하면 일반형 권장, 강제 전환 없음.
- 포함/제외·속성명·유형·옵션/색상·확인 완료 대상 보존. 질문과 CSV index/original의 출처 추적.
- 기본형 통합에서 이름/Title이 충돌하면 차단. 일반형은 사람 정보와 신청 맥락을 나누되 명시 대상 우선.

warnings·confirmationItems·blockingErrors를 분리했습니다. 확인 사항이 남아도 진단 계획은 내보낼 수 있으며 실행 승인/준비 완료가 아닙니다. 실제 ID는 logicalRef로 남고, 행 연결·고유 사람 중복 제거·계산값은 미실행/null입니다. 팀 참여기록 수 역시 고유 인원수와 구분합니다.

## API 제약

공식 문서와 기존 CLI 기준은 2026-03-11이며 CLI 버전은 변경하지 않았습니다. DB 컨테이너/초기 Data Source, data_source_id 기반 관계, 역속성 재조회와 기본 속성/계산의 실행 순서를 구분했습니다. Status 그룹 정의 변경은 UI 작업입니다.

기본 유형은 자동 계획, Relation/Rollup/Formula/Status는 실제 API 검증 필요, 임의 수식·알 수 없는 모듈은 미지원으로 표시합니다. 현재 Formula는 relation_count/equals_option만 지원하고, 계산 속성의 중첩 Rollup은 계획기 제한으로 차단합니다. 이것을 Notion 전체의 기능 제한이라고 주장하지 않습니다.

모든 결과에 liveApiVerified:false, futureExecutorReady:false, executionState:not_executed를 명시합니다. requestTemplates는 전부 executable=false이며 그대로 API에 보내는 JSON이 아닙니다.

## 재사용과 저장

previousPlan으로 논리 차이를 계산합니다. 팀 추가 예시는 공통 DB 3개 재사용·추가 DB 2개입니다. 요청 템플릿도 추가 DB만 POST하고 기존 DB는 GET/명시적 바인딩을 요구합니다. 기존 색상/속성 변경은 읽기/병합 제안으로 남기며 누락 옵션 자동 삭제를 하지 않습니다. 실제 원격 객체 재사용을 검증한 결과는 아닙니다.

Supabase/Auth/RLS/저장 version 1은 변경하지 않았습니다. 기존 저장값으로 계획을 재계산합니다. 구성 유형·모듈·추천 조건은 일시적 미리보기 선택으로 계정에 저장하지 않으며 새로고침 후 기본값으로 돌아갑니다. 계획/설정 JSON으로 보관할 수 있습니다. 이 제한을 화면과 문서에 표시했습니다.

기존 compileSchema·매핑 CLI·Notion PoC는 유지했습니다. 새 UI는 계획을 표시하고 기존 매핑 스키마 JSON은 호환용으로 구분합니다.
