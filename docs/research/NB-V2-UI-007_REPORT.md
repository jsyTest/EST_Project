## 2. 중복 원인과 최종 구조

index·mapping·result의 헤더 HTML에는 브랜드와 화면별 표시만 있다. 오른쪽 관리자 링크·이메일·로그아웃은 js/auth.js의 initializeAccount가 생성했다. 이 공통 함수가 관리자 페이지에서도 adminLink를 만들어 현재 페이지로 돌아오는 자기 링크를 붙이고 있었다. admin.html에는 별도로 브랜드 옆 복귀, 사이드바 하단 복귀, 권한 안내/설정 복귀 링크도 있었다.

### 일반 서비스

- 왼쪽: 기존 JPEG 심볼 + PPLUS + 기존 화면별 표시.
- 오른쪽: 서버 authorized 확인 후 관리자 페이지 → 이메일 → 로그아웃.
- index/mapping/result HTML은 수정하지 않았다.
- 일반 사용자·권한 확인 중·확인 실패에서는 기존 관리자 링크 hidden 처리 유지.

### 관리자 페이지

- 왼쪽: 기존 JPEG 심볼 + PPLUS만.
- 오른쪽: 서비스로 돌아가기(`/index.html`) → 이메일 → 로그아웃.
- admin.html에 정적 auth-account 슬롯과 복귀 버튼 1개를 두고, initializeAccount가 이 슬롯을 재사용해 이메일·로그아웃·오류 영역을 추가한다.
- adminPage에서는 adminLink를 생성하지 않는다. 그러나 roleController의 서버 권한 확인·상태 이벤트·게이트는 그대로 실행한다.
- 브랜드의 기존 index.html 링크와 aria-label은 보존했다.

### 제거/유지한 탐색

브랜드 옆 복귀 텍스트, 사이드바 복귀 링크, 현재 페이지로 가는 동적 관리자 자기 링크를 제거했다. 복귀 경로를 헤더 하나로 통합하기 위해 권한 안내·설정 안의 명시적 중복 복귀 링크도 제거했다. 브랜드 자체 클릭 이동은 유지한다.

사이드바에는 대시보드·회원 관리·이용 현황·설정 네 버튼만 있다. 설정 화면의 기존 로그아웃 액션은 유지했다. 메뉴 전환·프로필 표시·설정 로그아웃 이벤트 코드는 변경하지 않았다. 권한 확인 실패 시에도 인증된 사용자는 헤더의 안전한 복귀 경로를 사용할 수 있고 관리자 본문은 게이트로 차단된다.

## 6. Chrome 시각 검증의 구분

실제 계정 세션을 재사용하지 않았다. 가짜 JWT·신규 계정·새 인증 우회는 만들지 않았다. 설치된 Chrome 156을 새 임시 프로필로 실행하고 Supabase 요청을 차단했으며 실제 관측 요청도 0건이다.

허용된 두 방법을 구분했다.

1. 기존 `/__demo/admin.html`: 실제 소스의 관리자 HTML·CSS·기존 메뉴 전환을 렌더링하는 가상 시연. 헤더의 정적 복귀 버튼은 있지만 실제 계정 이메일/헤더 로그아웃은 생성하지 않는다.
2. 프로젝트 밖의 정적 헤더 문서 3개: 일반 서비스 관리자 표시 모형·일반 사용자 모형·관리자 헤더 모형. 헤더 HTML/CSS와 예시 이메일 텍스트를 넣었고 인증 스크립트·세션·JWT가 없다. 실제 앱의 게이트를 해제한 것이 아니며 별도 file 문서다. 로그아웃은 모양만 있고 동작하지 않는다. 모든 사진에 ‘정적 모형·인증 검증 아님’ 배너가 있다.

정적 모형은 CSS 배치 확인용이지 서버 권한 확인·실계정 버튼 표시 증거가 아니다. 일반 서비스의 권한에 따른 표시/차단은 별도의 Node 모의 테스트로 확인했다.
