## 5. 구 UI 캐시 현상

### 이번 재현 결과

기존 탭 진입·일반 새로고침·강력 새로고침·새 탭에서 모두 최신 단일 복귀 UI였습니다. **이번에는 구 UI가 재현되지 않았습니다.**

### 공개 파일과 응답 헤더

다음 6개 파일을 인증 없이 기본 GET / no-cache 요청 / ETag 조건부 요청으로 각각 읽었습니다. 총 18회입니다.

- admin.html, index.html, login.html
- js/auth.js, css/auth.css, css/admin.css

관찰 결과:

- 기본 GET과 no-cache 요청은 모두 200이며 로컬 소스와 바이트가 일치했습니다.
- 같은 ETag 조건부 요청은 모두 본문 없는 304였습니다. 본문 해시 비교에서 제외했습니다.
- Cache-Control은 18개 모두 public, max-age=0, must-revalidate였습니다.
- 기본 요청의 x-vercel-cache는 MISS, 후속 요청은 HIT였습니다. 200 응답의 Age는 0이었습니다.
- ETag와 Last-Modified를 기록했습니다. Vary·CDN-Cache-Control은 측정 응답에 없었습니다. 보이지 않는 내부 설정까지 없다고 단정하지 않았습니다.
- HTTP no-cache 요청은 브라우저 강력 새로고침과 별도 검사입니다.
- HIT나 304라는 사실만으로 구 UI 배포를 증명할 수 없습니다. 이번에 받은 본문은 최신 소스와 일치했습니다.

### 서비스 워커·파일 버전

- 제품 소스에서 서비스 워커 등록/CacheStorage 사용을 찾지 못했습니다. 공개 빌드 목록에도 서비스 워커가 없었습니다.
- 실제 Chrome의 과거 등록 이력이나 캐시 저장소는 조회하지 않아 브라우저 등록이 0개라고 단정하지 않았습니다.
- JS/CSS는 고정 파일명을 참조하며 파일명 내용 해시 방식은 아닙니다. vercel.json에 별도 캐시 헤더 설정은 없습니다.
- 개발 서버의 no-store는 로컬 설정이며 운영 응답과 구분했습니다.
- ETag/Last-Modified는 Git SHA 자체가 아닙니다. 문서만 다른 커밋은 같은 제품 파일 해시를 가질 수 있으므로 화면만으로 커밋을 추정하지 않았습니다.
